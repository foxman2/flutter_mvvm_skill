# 代码放在哪里

先遵守用户要求和项目约定。按当前需求选择需要的层，不要求每个功能都建齐下面的文件。

## 开始前

- 弄清页面状态、业务数据和业务规则分别由谁负责。简单任务直接写代码，不额外写架构报告或建空目录。
- 参考相似代码时，复用正确的命名和框架用法，不照搬错误的职责分工。
- 没有相似实现时，先读 `lib/mvvm/`、`lib/navigation/`、`lib/app_container.dart` 和 API 组装入口。不要猜框架方法，也不要把模板示例当成所有业务的标准。

## 文件分工

| 文件或类型 | 负责 | 不负责 |
|---|---|---|
| `*_page.dart` | 布局、渲染 Output、绑定 Input；管理 Context、controller、焦点、滚动和动画 | API 调用、JSON 解析、共享数据写入、业务规则和导航决策 |
| `widgets/*.dart` | 展示参数、传出 callback、维护必要的局部视觉状态 | 查找业务依赖、请求数据、持有具体 VM、决定路由 |
| `*_view_model.dart` | 页面输入、筛选、选中、草稿、请求结果、loading/error、导航和弹窗 | HTTP 细节、JSON 解析、跨页面缓存、独立业务规则、其他页面的私有状态 |
| `services/api/<domain>_api_service.dart` | 定义后台操作接口；Dio 实现负责请求、编码、调用 model 解析和转换协议错误 | 客户端业务决策、多接口业务流程、缓存、共享状态和 UI 反馈 |
| `services/api/api_service.dart` | 汇总 API 模块、配置 client、选择真实/Mock/未实现模块 | 聚合业务数据、业务判断和跨接口流程 |
| `services/mock_api/mock_<domain>_api_service.dart` | 实现同一接口，返回演示数据，模拟需要的服务端变化 | 客户端业务流程、页面状态、UI、客户端缓存和持久化 |
| `repositories/<domain>_repository.dart` | 数据读写、缓存、共享状态、协调数据源，提供统一数据入口 | Context、页面 loading、输入框状态、导航和无关业务流程 |
| `services/<domain>/*_service.dart`（业务 Service） | 独立业务计算或流程，例如排程、上传、跨业务操作 | 页面状态、UI、重复管理 Repository 已有的数据 |
| 请求/响应 model（DTO） | 已确认协议字段、允许值和 JSON 解析 | UI 状态、发请求、业务流程，把展示字段伪装成后台字段 |
| 领域 Model / 值对象 | 业务概念、自身规则、派生判断、相关字段一起变化的方法 | 网络或存储操作、全局容器、导航、调用服务查询外部数据 |
| `navigation/app_page.dart` | 强类型路由参数、转场、延迟创建页面和 VM、传入依赖 | 请求数据、权限或余额判断、页面业务流程 |
| `app_container.dart` | 创建和管理应用级依赖，是唯一全局依赖容器 | 业务规则、页面状态、转发业务操作 |
| `app.dart` / `main.dart` | 启动、初始化、应用配置、theme/l10n/路由；转交平台事件 | 页面流程、业务缓存、集中处理所有业务事件 |

一个业务接口和它的实现可以放在同一文件，不要求每个类型单独建文件。业务 Service 和 API Service 名称相似，但职责不同。

## 什么时候加一层

- 简单页面可以使用 `Page → ViewModel → API 接口`。
- 需要共享数据、缓存或协调数据源时，加 Repository。
- 有能独立说明的业务规则或流程时，再提取业务 Service。不要为每个按钮都创建 UseCase。
- 对象自身字段就能完成的判断，放在 Model。
- DTO 与业务含义一致时可以共用一个 model，不强制另建 Entity。
- 组件确实有复用需求，或拆出来能让局部职责更清楚时，才提取组件。

## 依赖怎么传

- AppContainer 和 ApiService 负责选择具体实现。AppPage provider 可以读取 `AppContainer.shared`，创建 VM 并传入依赖。
- VM、Repository 和业务 Service 通过构造函数接收依赖，不自行查全局容器，不判断 mock/real。
- API 实现接收配置好的 client、协议 model 和错误类型。按业务领域组织接口，不按页面建 API。
- Page 依赖对应 VM Type、展示组件、theme、l10n 和展示所需类型。Widget 接收展示参数和回调。
- Repository 可以接收 API、存储等数据依赖；业务 Service 可以接收 Repository、API 或其他职责明确的服务。
- 数据层和业务层不反向依赖 Page、具体 VM、路由或 UI 提示。
- 不允许循环依赖。出现双向调用时，把协调步骤放到调用方或独立业务流程。
- Service 和 Repository 不另加 `shared`。应用级实例由 AppContainer 管理生命周期。

## 数据由谁修改

- 同一份共享业务数据由一个 Repository 负责修改。页面可以读取结果、保存选中项和编辑草稿，不另建一份可独立修改的共享缓存。
- 草稿提交成功后，由数据负责人更新共享数据；取消编辑不能修改共享数据。
- 简单页面可以只在 VM 保存请求结果，不因数据来自后台就增加 Repository。
- 已有 Repository 管理的数据，读写经过它，避免漏掉缓存更新或失效处理。
- 业务步骤用直接调用串起来。订阅只用于需要接收的状态变化，不用事件总线或多个标记绕着传递命令。

## 容易混淆的情况

- API 可以编码请求、调用 `fromJson`、转换协议错误，不能决定是否购买、选择替代产品或自动执行下一项业务操作。
- 协议重试和鉴权沿用已有机制。按业务条件重试、补偿或回滚，由业务流程处理。
- 表单必填、即时提示和提交按钮状态由 VM 处理。与页面无关的有效性规则放在 Model 或业务 Service。客户端校验不替代服务端校验，也不编造后台规则。
- 合并资料和权益，供多个页面读写统一账号数据：用账号 Repository。
- 计算下一个发布时间：用纯函数或业务 Service。
- 协调上传和发布、处理步骤失败：用业务流程，数据读写仍经过对应的数据入口。
- 本页提交后关闭弹窗或跳转：放在 VM。两个列表同时展示，不代表必须新建聚合 Repository。

## Mock 和预览

- Mock 可以保存模拟服务端的内存记录，让创建或更新后的查询一致。排序、状态和计算按已确认或标记为临时的接口约定模拟。
- 客户端筛选交互、业务步骤和成功提示仍放在对应的 VM、Model 或业务 Service。
- “数据来自 Mock”不妨碍 VM 保存请求结果。正式和预览 VM 都不能自行编造业务数据。
- 预览只做用户要求的临时交互，不因此扩展为正式业务开发。
