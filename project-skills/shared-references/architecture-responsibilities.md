# MVVM 文件职责与依赖边界

用于决定代码归属；不要求每个功能都创建所有层。先遵守用户要求与项目明确约定，再按本规范检查相邻实现；已有代码只用于确认框架接口和有效模式，不作为复制越界职责的理由。

## 开始实现前

- 根据本次需求确定展示状态、业务数据和业务规则分别由谁负责，以及需要调用哪些依赖。简单任务直接在实现中体现，不额外生成架构报告或空目录。
- 有相似业务实现时，先检查其职责和依赖是否符合约束，再复用命名、框架与生命周期模式。
- 新项目没有相似业务实现时，读取 `lib/mvvm/`、`lib/navigation/`、`lib/app_container.dart` 和 API 组装入口，确认真实接口；按下面的职责选择最少的层，不把模板演示页面当作复杂业务的完整范例，也不猜测框架方法。

## 文件职责

| 文件 / 类型 | 负责什么 | 不负责什么 | 依赖边界与创建时机 |
|---|---|---|---|
| `*_page.dart` | 页面布局、渲染 Output、绑定 Input；管理 Context、输入框 controller、焦点、滚动和动画的生命周期 | 接口调用、JSON 解析、共享业务数据写入、业务规则和业务导航决策 | 依赖对应 ViewModel Type、展示组件、theme、l10n 和展示所需数据类型；页面按项目现有 Page 基类实现 |
| `widgets/*.dart` | 展示可复用或职责清晰的 UI 单元，通过 callback 暴露事件；维护必要的局部视觉状态 | 获取业务依赖、请求数据、持有具体 ViewModel、决定页面路由 | 依赖展示参数、UI 资源及必要的数据类型；稳定复用或清晰的局部职责成立时提取，不为猜测中的复用增加组件 |
| `*_view_model.dart` | 页面输入、筛选、选中、草稿、加载与错误呈现；响应操作、调用业务能力并通过 Output 提供展示状态；发出导航和弹窗意图 | HTTP 与序列化细节、跨页面权威数据缓存、独立领域规则、其他页面的私有状态 | 通过构造函数依赖 domain API contract、Repository 或业务 Service；不从全局容器取依赖，不持有 Context 或 controller |
| `services/api/<domain>_api_service.dart` | 定义后台操作 contract；Dio 实现负责请求、参数编码、调用 model 的解析方法，以及网络/协议错误转换 | 客户端业务决策、多接口业务流程、领域缓存、共享业务状态、loading/toast/导航 | 依赖已配置的 HTTP client、协议 model 和错误类型；按后台业务领域组织，复用已有 domain，不按页面创建 API |
| `services/api/api_service.dart` | 汇总 domain 模块，配置基础 client，在组装时选择 real/mock/未实现模块 | 聚合业务数据、判断业务条件、执行跨接口业务流程 | 只在组装边界依赖具体 API 实现；已有入口继续扩展，不另建第二个全局入口 |
| `services/mock_api/mock_<domain>_api_service.dart` | 实现同一 contract，提供 fixture；模拟必要的延迟、空结果、错误和服务端数据变化 | 客户端业务流程、页面状态、UI 反馈，以及替代 Repository 的客户端缓存或持久化 | 依赖 contract 和正式或临时 model；仅为所需演示/测试场景创建，不实现另一个客户端业务系统 |
| `repositories/<domain>_repository.dart` | 管理领域数据的读取与更新、缓存、共享状态和数据源协调；按需聚合接口数据，对外提供一致的数据入口 | Widget/Context、页面 loading、输入框状态、导航、任意跨领域流程的杂物集合 | 构造注入 API contract、存储或明确的数据依赖；存在数据管理责任时创建，不为每个 API 增加纯转发 Repository |
| `services/<domain>/*_service.dart`（业务 Service） | 可独立描述的领域计算或流程，例如排程计算、上传执行、跨领域操作协调 | 页面交互状态、UI 呈现、重复维护 Repository 已拥有的数据 | 按需要注入 Repository、API contract 或其他有明确职责的服务；独立规则、流程或复用边界成立时提取，不强制每个动作创建 UseCase |
| request/response model（DTO） | 表达已确认协议字段、序列化、反序列化及协议允许值 | UI 状态、发请求、业务流程；不能为方便页面而把派生展示字段伪装成后台字段 | 依赖序列化支持和嵌套数据类型；协议需要时创建，解析规则留在 model 内 |
| 领域 Model / 值对象 | 表达业务概念、自身不变量、派生判断和有业务含义的状态变化方法 | 网络或存储 I/O、全局容器、导航、依赖其他服务完成外部查询 | 依赖数据类型和纯计算；稳定业务概念或约束存在时创建。协议与领域语义一致时可复用一个 model，不机械复制 DTO 与 Entity |
| `navigation/app_page.dart` | 强类型路由参数、转场信息、页面与 ViewModel 的延迟构造和注入 | 请求数据、权限/余额等业务判断、执行页面操作流程 | 可在 provider 中读取 AppContainer 并构造页面依赖；新增可导航页面时增加对应 case |
| `app_container.dart` | 创建、装配并管理应用级依赖及其生命周期，作为唯一全局依赖容器 | 业务规则、页面状态、业务操作的转发方法 | 可依赖具体实现以完成装配；共享实例按实际生命周期注册，Service/Repository 不另设 `shared` |
| `app.dart` / `main.dart` | 启动与初始化接线、应用配置、theme/l10n/路由挂载，将平台生命周期事件转交明确所有者 | 页面业务流程、领域数据缓存或集中处理所有业务事件 | 依赖应用级配置与入口；复用既有启动结构，不为单个功能修改通用启动流程 |

文件按职责内聚；一个 domain 的 contract 与实现可以同文件，不要求“一种类型一个文件”。业务 Service 与 API Service 虽然都叫 Service，职责不同，不能因名称相近而混放逻辑。

## 依赖与状态所有权

- 常见调用方向为 `Page → ViewModel → API contract`，需要数据管理时使用 `Page → ViewModel → Repository → API contract/存储`；独立业务流程由 ViewModel 调用业务 Service，再协调所需的数据能力。这些是可选路径，不是每个功能必经的链条。
- 数据层和业务层不反向依赖 Page、具体 ViewModel、路由或 UI 反馈。Repository 与业务 Service 不形成循环依赖；出现双向调用时，明确数据所有者，把协调步骤移到调用方或独立流程中。
- 实现选择由 AppContainer/API 组装边界完成；ViewModel、Repository 和业务 Service 使用注入依赖，不自行查找 `AppContainer.shared`，也不判断 mock/real。
- 同一份可变业务数据只有一个客户端权威所有者。需要共享时由 Repository 管理，页面通过输出获取快照或投影；页面可以保留加载结果、选中项与编辑草稿，但不能再维护可独立写入的共享数据副本。草稿提交成功后由数据所有者更新，取消草稿不修改共享数据。
- 简单页面未使用 Repository 时，ViewModel 可以持有本页请求结果；不因“数据来自后台”就强制增加 Repository。已有 Repository 管理该数据时，页面写入必须经过该入口，避免绕过缓存更新或失效逻辑。
- 命令通过明确调用执行；订阅用于接收实际需要的状态变化。不要用事件总线或多个布尔字段隐式串联业务步骤。

## 边界判断

### 接口适配与业务决策

API Service 可以把请求 model 编码后发送、调用 `fromJson` 解析响应、按已确认协议转换错误；不能自行判断是否允许购买、选择替代产品，或在一个请求后自动执行另一个业务动作。协议内重试、鉴权等基础设施沿用项目已有机制；按业务条件重试、补偿和回滚由流程所有者处理。

表单必填、即时输入提示和提交中的按钮状态由 ViewModel 协调；与页面无关的业务有效性规则放在领域 Model 或业务 Service。规则依赖的数据由 Repository/API 提供。客户端校验不代替服务端最终校验，也不重复编造未确认的后台规则。

### Repository 与业务 Service

按操作目的判断，不按接口数量判断：

- 合并资料与权益、维护统一账号快照，并让多个页面读取和更新：归账号 Repository。
- 计算下一个可发布时间：归纯业务函数或业务 Service；仅依赖对象自身字段的判断可以放在 Model。
- 按规则协调上传与发布、处理步骤失败：归独立业务流程；数据读写仍经过其所有者，不由 API Service 串联。
- 本页提交成功后关闭弹窗或跳转：归 ViewModel。两个独立列表仅在本页一起展示，不因此强制创建聚合 Repository。

### Mock 与页面结果

Mock 可以在模拟创建成功后保存内存记录，让后续查询返回该记录，这是模拟服务端行为。排序、状态和计算若属于接口返回语义，也可按已确认或明确标记的临时 contract 模拟；客户端特有的筛选交互、业务编排和页面成功反馈仍由其各自所有者处理。

“演示数据来自 Mock”约束的是数据来源，不禁止 ViewModel 持有请求得到的结果。正式与预览 ViewModel 都不能自行生成业务 fixture；预览只实现授权的临时交互，不借职责划分扩展为正式业务开发。

## 完成前检查

检查本次修改的文件、依赖与调用方，修复越界后再交付；不要求机械输出检查报告：

- 每个新增文件能说明具体职责；不存在以 Manager/Helper/Service 名义收纳无关流程，或只为层数齐全而新增的空壳。
- API 只适配接口；数据更新有统一所有者；Model 的规则无需访问全局依赖；页面交互与数据管理没有混在一起。
- 依赖方向无循环，业务对象经构造注入，导航与 UI 反馈留在展示层。
- 页面快照、共享数据与编辑草稿已区分，避免重复写入、过期缓存和取消编辑污染共享数据。
- 沿用代码前检查其职责，不把已有违规实现当作新功能的标准；修复范围限于当前任务及必要调用方，不借检查重构无关功能。
