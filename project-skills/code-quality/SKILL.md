# Code Quality

在满足正确性、安全性和明确需求的前提下，把可读性作为有效方案之间的首要选择标准。适配当前项目，只引入解决当前问题所需的设计。

## 工作流程

1. 先读取适用的项目说明、相邻代码、测试以及 formatter、lint、类型检查配置，识别当前语言版本、架构边界、命名和错误处理约定。
2. 明确需要保留的行为、公共接口和兼容性边界。用户只要求审查或诊断时，不修改代码。
3. 选择能完整满足需求的最小方案。优先沿用项目已有模式；只有现有模式明显损害正确性、安全性或可读性时才局部偏离，并说明原因。
4. 实现或评审后，重新从首次阅读代码的维护者视角检查命名、控制流、状态变化、依赖关系和错误路径。
5. 使用项目已有工具执行与风险相称的验证，并报告未能完成的检查。

## 可读性原则

- 使用能表达领域含义和职责的名称，并在同一概念上保持术语一致。
- 优先使用直接、可顺序阅读的控制流；消除不必要的嵌套、隐式状态、聪明但难懂的表达式和代码高尔夫。
- 让函数、类型和模块各自承担一个清晰职责。只有提取后能提供有意义的名称、稳定复用或必要测试边界时才增加新单元。
- 让相关数据和行为尽量靠近，使状态变化、依赖和副作用在调用处可见。
- 只在代码本身无法说明原因、约束或取舍时添加注释；不要用注释复述实现。
- 明确处理边界与失败路径，不静默忽略错误，也不使用掩盖真实问题的宽泛兜底。
- 遵循目标语言和当前项目的惯用写法，不强制跨语言的函数行数、复杂度阈值、目录结构或固定架构。

## 避免过度设计

- 不为假设中的未来需求增加接口、基类、工厂、构建器、层级、扩展点、配置项或通用框架。
- 不为一次性实现引入新依赖；优先使用语言标准能力和项目已有依赖。
- 只抽象当前代码中已经稳定存在的共同概念。少量清晰重复优于隐藏差异或增加跳转成本的错误抽象。
- 不顺手重构、重命名或格式化与任务无关的代码。
- 不进行没有需求、测量或证据支持的性能优化。

## 按任务执行

- **实现或修改**：提交最小、行为完整的改动；保持公共接口稳定，并让新代码自然融入相邻实现。
- **重构**：先确认行为基线和保护性测试，再分离结构调整与行为变化；不要用重写替代可控的小步修改。
- **代码审查**：只报告会具体影响理解、维护、正确性或测试性的发现。为每项发现给出位置、影响和最简单的改进方向；不要把纯个人风格偏好当作问题。没有实质发现时明确说明，并指出验证范围。

## 验证

- 优先运行最接近改动的 formatter、lint、类型检查和测试，再按风险决定是否扩大范围。
- 检查最终差异，确认没有无关改动、模板占位符、死代码、过时注释或无需求支撑的抽象。
- 无法运行工具或测试时，说明原因、已完成的替代检查和剩余风险，不把未执行描述为已通过。
