# Flutter MVVM Test

## 工作流程

1. 确认项目包含 `pubspec.yaml` 和 `lib/`，读取受测代码、已有 `test/`、相邻测试、测试依赖和最近相关改动。
2. 区分纯视觉、非视觉和混合改动：纯视觉任务不新增或修改测试；非视觉部分从用户可观察行为和稳定 contract 定义覆盖；混合改动只验证行为部分。
3. 检查已有测试是否直接断言受影响的输入、动作、状态、输出或 contract；覆盖充分时复跑并记录依据，覆盖不足时才新增或更新最小测试。
4. 区分评审、仅运行、补测试或覆盖率、复现缺陷和修复失败；评审或仅运行时保持代码只读，除非用户明确要求修改测试。
5. 选择能稳定覆盖行为的最小测试层级；修复回归时先收敛已有失败测试，或新增能稳定复现问题的失败测试，再判断失败来自测试本身还是生产代码。
6. 复用项目现有测试工具，优先直接构造依赖并使用小型 fake；只有现有方案无法清晰表达行为时才增加测试依赖。
7. 在测试内创建 controller、stream、subscription 或其他有生命周期的资源后立即用 `addTearDown` 注册清理；`setUp` 创建的 fixture 用 `tearDown` 恢复，且控制时间、随机数和共享状态，不使用真实网络或任意延迟。
8. 新增或修改测试时格式化改动文件，运行目标测试、受影响的测试集和 `flutter analyze`；涉及共享或全局状态时，再用明确 seed 运行 `--test-randomize-ordering-seed`，并记录失败 seed。
9. 只有用户明确要求数值覆盖率时，才在修改前用 `flutter test --coverage` 建立基线，并在修改后用相同范围复测；按风险补行为，不为追求百分比固化无价值实现细节。
10. 只在用户要求或改动范围需要时扩大到完整测试集；交付时列出复用或新增的覆盖、实际命令、结果、覆盖率口径和仍未覆盖的风险。

## 关键边界

- 测试公开行为和稳定 contract，不锁定私有字段、内部调用次数、无语义布局细节或生成代码实现。
- 只有测试直接断言受影响行为或 contract 才算已有覆盖；仅执行到相关代码或拥有行覆盖不算。
- 纯布局、颜色、字体、间距、圆角、阴影、图标、静态 fixture 和静态文案不机械增加测试；它们一旦影响状态分支、callback、交互、导航或动态输出，就按行为改动处理。
- 不为仅由编译器和 analyzer 约束且不改变可观察行为的结构机械增加测试；model 解析、序列化和其他 contract 变更仍需直接行为覆盖。
- 普通 Service、Repository 和 ViewModel 测试直接注入依赖；只通过项目已有公开 API 验证 `AppContainer` 等全局入口。
- 全局入口没有可恢复 API 时，把初始化前后行为放在同一个测试或隔离文件中，不依赖测试声明顺序，也不为测试擅自新增全局替换或重置入口。
- 不用放宽断言、延长任意等待、用 `pumpAndSettle()` 掩盖未收敛任务或吞掉异常来消除失败。
- 测试暴露生产缺陷时保留最小复现并说明原因；除非用户明确要求修复生产行为，否则不修改生产实现。
- golden、端到端和设备集成测试只在项目已有约定或用户明确要求时采用。
