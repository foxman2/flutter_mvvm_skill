# Flutter MVVM Test

## 工作流程

1. 确认项目包含 `pubspec.yaml`、`lib/` 和 `test/`，读取受测代码、相邻测试、现有测试依赖和最近相关改动。
2. 从用户可观察行为和回归风险定义断言，选择能稳定覆盖该行为的最小测试层级。
3. 修复回归时先写出能稳定复现问题的失败测试，再判断失败来自测试本身还是生产代码。
4. 复用项目现有测试工具，优先直接构造依赖并使用小型 fake；只有现有方案无法清晰表达行为时才增加测试依赖。
5. 控制异步、时间、全局容器和流的生命周期，避免真实网络、任意延迟、测试顺序依赖和未恢复的共享状态。
6. 格式化测试文件，运行目标测试，再运行受影响的测试集和 `flutter analyze`；只在用户要求或改动范围需要时扩大到完整测试集。
7. 交付时列出新增或修改的行为覆盖、实际运行的命令、结果以及仍未覆盖的风险。

## 关键边界

- 测试公开行为和稳定 contract，不锁定私有字段、内部调用次数、无语义布局细节或生成代码实现。
- 不为简单 DTO 直映射、静态 fixture、纯文案或编译器和 analyzer 已约束的结构机械增加测试。
- 只在验证依赖装配时操作 `AppContainer` 等全局入口，并在每个测试结束后恢复状态。
- 不用放宽断言、增加无界 `pumpAndSettle()` 或吞掉异常来消除失败。
- 测试暴露生产缺陷时保留最小复现并说明原因；除非用户明确要求修复生产行为，否则不修改生产实现。
- golden、端到端和设备集成测试只在项目已有约定或用户明确要求时采用。
