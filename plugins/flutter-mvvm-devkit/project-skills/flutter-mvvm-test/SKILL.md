# Flutter MVVM Test

## 工作流程

1. 确认项目包含 `pubspec.yaml` 和 `lib/`，读取受测代码、已有 `test/`、相邻测试、测试依赖和最近相关改动；需要新增测试时才创建缺少的测试目录。
2. 区分评审、仅运行、补测试或覆盖率、复现缺陷和修复失败；评审或仅运行时保持代码只读，除非用户明确要求修改。
3. 从用户可观察行为和回归风险定义断言，选择能稳定覆盖该行为的最小测试层级。
4. 修复回归时先收敛已有失败测试，或新增能稳定复现问题的失败测试，再判断失败来自测试本身还是生产代码。
5. 复用项目现有测试工具，优先直接构造依赖并使用小型 fake；只有现有方案无法清晰表达行为时才增加测试依赖。
6. 在测试内创建 controller、stream、subscription 或其他有生命周期的资源后立即用 `addTearDown` 注册清理；`setUp` 创建的 fixture 用 `tearDown` 恢复，且控制时间、随机数和共享状态，不使用真实网络或任意延迟。
7. 新增或修改测试时格式化改动文件，运行目标测试、受影响的测试集和 `flutter analyze`；涉及共享或全局状态时，再用明确 seed 运行 `--test-randomize-ordering-seed`，并记录失败 seed。
8. 只有用户明确要求数值覆盖率时，才在修改前用 `flutter test --coverage` 建立基线，并在修改后用相同范围复测；按风险补行为，不为追求百分比固化无价值实现细节。
9. 只在用户要求或改动范围需要时扩大到完整测试集；交付时列出覆盖行为、实际命令、结果、覆盖率口径和仍未覆盖的风险。

## 关键边界

- 测试公开行为和稳定 contract，不锁定私有字段、内部调用次数、无语义布局细节或生成代码实现。
- 不为简单 DTO 直映射、静态 fixture、纯文案或编译器和 analyzer 已约束的结构机械增加测试。
- 普通 Service、Repository 和 ViewModel 测试直接注入依赖；只通过项目已有公开 API 验证 `AppContainer` 等全局入口。
- 全局入口没有可恢复 API 时，把初始化前后行为放在同一个测试或隔离文件中，不依赖测试声明顺序，也不为测试擅自新增全局替换或重置入口。
- 不用放宽断言、延长任意等待、用 `pumpAndSettle()` 掩盖未收敛任务或吞掉异常来消除失败。
- 测试暴露生产缺陷时保留最小复现并说明原因；除非用户明确要求修复生产行为，否则不修改生产实现。
- golden、端到端和设备集成测试只在项目已有约定或用户明确要求时采用。
