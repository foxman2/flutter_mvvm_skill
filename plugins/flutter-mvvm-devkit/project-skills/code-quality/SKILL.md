# Code Quality

在满足正确性、安全性和明确需求的方案之间，把可读性作为有效方案之间的首要选择标准。适配当前项目，不套用跨语言的固定风格。

## 工作流程

1. 明确需要保留的行为、公共接口和兼容性边界，并读取相邻代码与项目约定。
2. 选择完整满足当前需求的最小方案；优先沿用现有模式，必要偏离时说明原因。
3. 从维护者视角检查命名、控制流、状态变化、依赖和失败路径，并检查新增或修改代码的关键注释是否充分。
4. 遵循项目已有验证要求，使用项目已有工具执行与风险相称的验证，并检查最终差异。

## 判断原则

- 使用领域含义清楚且一致的名称，优先选择可顺序阅读的直接控制流。
- 让函数、类型和模块承担清晰职责；只有提取后能形成稳定概念、复用或测试边界时才增加抽象。
- 让相关数据和行为靠近，使状态变化、依赖和副作用可见。
- 为公开入口、关键业务规则、边界约束、复杂控制流、异步或状态变化以及不直观的实现添加注释，使维护者能够理解用途、原因和限制。注释解释代码无法表达的意图、约束或取舍，不复述实现；简单且自解释的代码无需强行添加注释。
- 遵循目标语言和当前项目的注释惯例。公开接口优先使用文档注释，按需说明职责、调用时机、关键输入与输出、状态变化或副作用、失败方式和不能破坏的业务约束；复杂实现使用局部注释，解释业务原因、顺序依赖、并发保护和边界选择。无法从上下文确认的信息不得编造。
- 明确处理边界和错误，不用宽泛兜底掩盖问题。
- 遵循目标语言和当前项目惯用写法，不强制跨语言的函数行数、复杂度阈值、目录结构或固定架构。
- 不为假设中的未来需求增加层级、扩展点、配置、依赖或通用框架。
- 少量清晰重复优于隐藏差异的错误抽象；不顺手重构无关代码或做无证据的性能优化。

## 按任务执行

- **实现或修改**：保持改动小而完整，并让新代码自然融入相邻实现。
- **重构**：先确认行为基线，再把结构调整与行为变化分开。
- **代码审查**：只报告有具体影响的发现，给出位置、影响和最简单的改进方向；不要把个人偏好当作问题。
