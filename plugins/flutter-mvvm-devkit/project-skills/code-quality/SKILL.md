# Code Quality

满足当前需求，保证正确和安全，再选最容易读懂的写法。遵循项目已有约定。

## 先看需求

- 先读项目约定和相关代码，弄清这次要做什么、哪些行为要保留。
- 不要因为“理论上可能出问题”就增加代码。当前需求没有要求，实际使用中也几乎不会遇到的情况，不为它专门增加判断、兜底或抽象。发现一种可能性，不等于必须处理它。
- 先检查公共层是否已经处理 loading、错误、重复请求和页面销毁。业务代码不要重复处理。
- 旧代码和旧测试不自动等于需求。需求已改变时，同步删除旧逻辑、更新测试。

## 把流程写直接

- 按钮要做什么，就在回调里直接调用。不要先记一个标记，再到别处判断标记做事。
- 能用直接调用和顺序 `await` 完成的流程，不用监听或事件广播串起来。
- 需要持续保存状态、等待多个事件，或响应 UI 和系统事件时，才使用状态或监听。监听用完要释放。
- 名称说清业务含义。条件尽量正着写，例如 `createsNewPost`。
- 处理当前流程会遇到的错误，不用空 catch 或默认成功掩盖失败。

## 管好数据和职责

- 业务规则放在拥有数据的模型里。调用方不要反复组合字段来猜业务状态。
- 必须一起修改的字段，由模型提供一个方法一起改，例如 `withSchedule`。
- 一组字段确实代表同一个业务概念时，可以用值对象或 sealed 类型限制错误组合。不要只靠注释或 `assert` 保证重要规则，也不要为一次简单判断新建类型。
- 明确数据由谁修改。编辑副本、提交、取消和缓存更新不能绕过统一的数据入口。
- 按项目分工放代码，不把网络协议、数据管理、业务规则和 UI 交互混在一起。不要复制已有的错误分工。
- 避免循环依赖、到处查找全局对象，以及把无关功能塞进工具类。

## 少加东西

- 新增类、层、配置或依赖，必须能解决当前的具体问题。不要为以后可能用到而提前设计。
- 不为了凑分层增加纯转发代码。少量重复可以接受，不要为了复用把不同逻辑硬合在一起。
- 注释解释“为什么这样做”和必要限制，不复述代码。公开接口按项目习惯写文档注释，简单代码不用硬加注释，不确定的原因不要编。
- 不套用固定架构、行数限制或其他语言的习惯。不顺手重构无关代码，不做没有依据的性能优化。

## 修改和审查

- 修改要小而完整，同步更新调用方，清理废弃代码。
- 重构前确认要保留的行为。若也改变了行为，要明确说明。
- 审查只报告当前支持的流程中有实际影响的问题。说清位置、触发方式、后果和最简单的修法。不要把个人偏好或假设场景当成 bug。
- 用户只要求审查时，先报告，不直接修改代码。
- 按项目要求运行与改动相关的检查，查看最终 diff。测试失败时先判断是代码问题还是旧断言已不适用。
